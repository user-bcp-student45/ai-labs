## H-API-01 — Token Base64 con secreto embebido

- **Hallazgo:** `HALLAZGOS.md`, H-API-01, estado Aprobado; evidencia: `api/app/main.py:14,17-25`.
- **Problema:** `legacy_identity` decodifica un valor Base64 con un secreto fijo y sin firma, emisor ni audiencia; los errores internos se concatenan a la respuesta 401. El formato heredado no puede probar autenticidad criptografica.
- **Cambio propuesto:** sustituir la decodificacion artesanal por verificacion JWT con firma, algoritmo permitido, emisor, audiencia y expiracion obligatorios. Leer el material de firma y los valores de issuer/audience de configuracion externa; no incluir secretos en el repositorio. Rechazar tokens invalidos con mensaje 401 generico y sin exponer excepciones. Preservar el esquema de credencial HTTP `Authorization` y mantener las rutas/respuestas de API. Coordinar con el emisor externo la emision de JWT compatible y el despliegue de configuracion antes de activar la verificacion; no se inspecciona ni cambia el componente emisor en este alcance.
- **Dependencia:** evaluar una biblioteca JWT mantenida (por ejemplo PyJWT) y justificar su necesidad frente a la verificacion estandar; fijar version compatible solo tras revisar advisories. Es una dependencia nueva potencial y requiere coordinacion/aprobacion de suministro antes de incorporarla.
- **Coordinacion registrada:** el solicitante autorizo usar e instalar el PyJWT 2.15.1 ya declarado; no hay evidencia de una revision de suministro adicional. La consulta del GitHub Advisory Database para GHSA-752w-5fwx-jx9f / CVE-2026-32597 indica versiones afectadas `<= 2.11.0` y correccion desde 2.12.0; el pin actual queda fuera de ese rango. Esta comprobacion no sustituye una atestacion organizacional de suministro.
- **Archivos a tocar:** `api/tests/test_api.py` (caracterizacion y pruebas de tokens); `api/app/main.py` (dependencia de autenticacion o integracion con ella); configuracion/manifiesto en `api/` solo si la biblioteca/configuracion lo requiere. Si la separacion de capas se realiza en H-API-06, implementar el verificador en su modulo de seguridad y no duplicarlo en `main.py`.
- **Caracterizacion previa:** con app/DB temporales, comprobar el flujo actual: token Base64 vigente aceptado, token vencido rechazado con 401 y ruta protegida rechaza credencial malformada. Capturar codigo y forma de respuesta sin fijar el texto de excepcion como contrato. Antes de desplegar el nuevo verificador, probar token firmado valido y rechazos por firma, issuer, audience y expiracion; mantener los mismos endpoints y respuestas de negocio.

## H-API-02 — Acceso y asignacion de tareas por `owner` del cliente

- **Hallazgo:** `HALLAZGOS.md`, H-API-02, estado Aprobado; evidencia: `api/app/main.py:68-70,78-84,91-93`.
- **Problema:** `GET /api/tasks` y `GET /api/summary` permiten seleccionar otro propietario por query; `POST /api/tasks` permite elegir propietario en el cuerpo. Esto quiebra el aislamiento entre identidades.
- **Decision de compatibilidad aprobada por el solicitante:** ignorar el `owner` enviado por el cliente y forzar siempre el owner de `identity["username"]` verificado, tanto en lecturas como en creaciones. El campo y la query se conservan por compatibilidad de forma, pero no controlan la identidad autorizada.
- **Archivos a tocar:** `api/tests/test_api.py`; funciones de ruta/servicio y repositorio que listan, resumen o crean tareas en `api/app/main.py` o los modulos de capas creados en H-API-06.
- **Caracterizacion previa:** con datos semilla aislados y token de `student`, verificar que omitir `owner` lista/resume solo student; registrar tambien el comportamiento actual con `owner=trainer` y con `owner=trainer` en el cuerpo de creacion. Luego agregar regresiones: student no obtiene datos de trainer ni crea una tarea propiedad de trainer; el comportamiento ante owner discrepante corresponde a la decision de compatibilidad acordada; probar que los campos de respuesta siguen presentes.

## H-API-03 — Filtros e inserts SQL concatenados

- **Hallazgo:** `HALLAZGOS.md`, H-API-03, estado Aprobado; evidencia: `api/app/main.py:70,84,93`.
- **Problema:** filtros de tareas/resumen y valores insertados se interpolan en SQL. Entradas con caracteres SQL pueden alterar consultas, generar errores o afectar registros.
- **Cambio propuesto:** mover acceso SQL a repositorio (coordinado con H-API-06) y usar placeholders SQLite en todos los valores. Usar el ID generado como parámetro al recuperar la tarea creada. No construir SQL concatenando valores del usuario. Mantener orden, campos y estructura de respuestas observados.
- **Archivos a tocar:** `api/tests/test_api.py`; módulo actual `api/app/main.py` y repositorio SQLite nuevo dentro de `api/` bajo H-API-06.
- **Caracterizacion previa:** comprobar listado ordenado por ID, creación HTTP 201 con valores normales y resumen correspondiente en DB temporal; registrar que las respuestas mantienen nombres de campo observados. Después agregar casos con comillas/caracteres de control ordinarios como datos literales y verificar que no cambian el conjunto de filas ni causan fallo SQL. Evitar payloads destructivos.

## H-API-04 — Nombre y contenido del archivo subido sin controles

- **Hallazgo:** `HALLAZGOS.md`, H-API-04, estado Aprobado; evidencia: `api/app/main.py:107-111`.
- **Problema:** el nombre controlado por el cliente se usa para formar la ruta de escritura y el contenido completo se lee sin limite; no hay filtro de extensiones. Puede producir escritura fuera del directorio esperado, tipos no permitidos o consumo excesivo de disco/memoria.
- **Cambio propuesto:** normalizar y validar el nombre en una funcion dedicada; aceptar solo extensiones permitidas mediante constante nombrada; limitar bytes leidos antes de persistir, rechazando excedentes con un error HTTP claro y generico. Resolver la ruta final y asegurar que permanece dentro del directorio de uploads. Preservar `POST /api/requirements`, el campo multipart `file` y la forma exitosa `{owner,fileName,storedAt,size}`; `fileName` debe representar el nombre seguro guardado. Definir los limites y extensiones como decision de producto antes de implementar, dado que el contrato actual no los especifica.
- **Archivos a tocar:** `api/tests/test_api.py`; manejador de carga en `api/app/main.py` o servicio de archivos bajo H-API-06; configuracion en `api/` solo si se acuerdan limites externalizados.
- **Caracterizacion previa:** usar `tmp_path` y un archivo pequeno `requirements.txt`; comprobar HTTP 201, claves de respuesta y contenido guardado en el directorio temporal. Agregar pruebas para nombre normalizado/seguro, extension rechazada, limite excedido y ruta final dentro del directorio. Probar nombres de traversal solo en ubicaciones temporales y comprobar que no se escribe fuera del directorio permitido.

## H-API-06 — Rutas, persistencia, reglas y serializacion en un modulo

- **Hallazgo:** `HALLAZGOS.md`, H-API-06, estado Aprobado; evidencia: `api/app/main.py:29-59,67-124`.
- **Problema:** `api/app/main.py` inicializa SQLite y contiene definicion de rutas, SQL, reglas de resumen, serializacion y escritura de archivos, lo que dificulta cambiar y probar responsabilidades independientemente.
- **Cambio propuesto:** refactor incremental en capas FastAPI (rutas/HTTP), servicios (reglas y coordinacion) y repositorios (SQLite parametrizado). Definir modelos Pydantic de request/response y mapper para conservar exactamente campos/tipos JSON observados. Mantener `create_app(db_path, upload_dir)` como punto de composicion y conservar endpoints y codigos de exito. H-API-01 y H-API-03 se integran en seguridad/repositorio sin duplicar logica; H-API-04 se delega a servicio de archivos. No duplicar conversiones de tareas ni reglas.
- **Archivos a tocar:** `api/app/main.py`; nuevos modulos dentro de `api/app/` para modelos, rutas, servicios, repositorios y seguridad/archivos solo cuando necesarios; `api/tests/test_api.py`.
- **Caracterizacion previa:** antes del movimiento, ampliar pruebas para listar tareas semilla con claves/valores y orden, crear tarea y verificar respuesta/summary, obtener summary de dataset conocido, cargar archivo valido y comprobar `backend-health` mediante stub controlado (sin depender del servicio auth real). Ejecutar pruebas existentes y nuevas en cwd `api/`; comparar respuestas, status codes, aislamiento temporal y cierre de conexion antes/despues del refactor.

## H-API-07 — Tipos crudos, excepciones amplias y condicionales anidados

- **Hallazgo:** `HALLAZGOS.md`, H-API-07, estado Aprobado; evidencia: `api/app/main.py:17-25,56,68,78,91-105,115-121`.
- **Problema:** uso de `dict[str, Any]` para entradas/salidas, captura de excepciones generales y condicionales anidados hacen ambiguos los datos admitidos y el manejo de errores. La duplicacion listada como candidata en `RETO.md` no quedo confirmada como caso independiente en Discovery; revisar durante la implementacion antes de extraer helpers.
- **Cambio propuesto:** introducir modelos Pydantic tipados para los contratos request/response y anotaciones concretas para identidad, filas transformadas y resumen; separar validacion/serializacion de rutas. Capturar excepciones especificas y traducir errores esperados a `HTTPException` con mensajes no sensibles; en `backend_health`, manejar fallos de transporte/timeout de forma explicita y mantener el formato de respuesta existente si esa es la politica de contrato acordada. Extraer la regla de conteo de prioridad abierta a una expresion/funcion simple y reutilizable solo si evita duplicacion real.
- **Archivos a tocar:** `api/tests/test_api.py`; `api/app/main.py` y modelos/servicios nuevos de H-API-06. `api/requirements.txt` unicamente si la funcionalidad Pydantic necesaria no estuviera disponible en la version instalada, lo cual debe verificarse primero.
- **Caracterizacion previa:** comprobar esquema JSON exitoso de listar/crear/resumen/carga, defaults actuales al crear tarea, rechazo de token invalido y respuesta actual de backend-health usando stub para exito y fallo. Luego validar entradas invalidas con errores controlados y confirmar que respuestas exitosas mantienen las mismas claves/tipos y que ninguna respuesta expone texto crudo de excepcion.
